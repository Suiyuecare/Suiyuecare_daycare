# 第02包：主管開站準備清單（本機實作）

## 實作範圍

- 既有第58頁「機構資料」內嵌完整清單，由主要整合工作接線；今日工作提供主管入口，不取代原有89頁。
- 9項檢查：機構、員工帳號／聘僱、員工證照／服務資格、個案收案、緊急聯絡／同意、當日分工、照顧依據、安全審查、備援演練。
- 各項顯示負責角色、缺件說明與既有補正頁；專業依據折疊，不隱藏安全限制。沒有人工勾選即可通過的按鈕。
- 目前分支由已驗證的`TenantContext`決定，不接收網址指定分支；日期僅傳入實際支援的`effectiveOn`與`date`查詢參數。
- 照顧分工去重個案人數，但保留上午／下午班次；有工作安排不等於已完成照顧。
- 桌機可比較狀態與處理入口；手機卡片自然換行，觸控控制至少44px；載入、離線、資料過期及無權限狀態各別呈現。

## 真實資料與權限邊界

`loadOpeningReadinessSnapshot`只在伺服器呼叫現有機構、員工、個案主檔、照顧分工的授權讀取函式，沿用其RPC／RLS與查閱稽核；不新增管理金鑰、跨分支查詢或寫入。先檢查機構管理員／分支主管角色，家屬、維運及一般照服員不可取得彙總。

機構／員工快照若需額外權限或既有AAL2而本次會話不符，該來源標為「目前無法核對」，不降低保護，也不顯示0。各來源分開失敗；依賴員工及個案的照顧分工在任一來源失敗時不可通過。

個案來源`client_master_snapshot`既有讀取函式逐列核對機構／分支、唯一識別及代碼；同時核對`visible_count`與完整筆數，上限10,000，截斷則拒絕。本清單只產生彙總說明，不傳個案／員工姓名、代碼、身分識別、電話、醫療內容或附件。

原始機構與員工資料有截斷、過期或不符分支時不通過。個案名冊新鮮度由伺服器取得時間核對；頁面超過一分鐘提示重新檢查。各來源並行查詢，這是分項準備檢查，不宣稱跨來源單一資料庫交易快照。

只有明確`demo:true`使用合成fixture，與正式缺件處理分開，不能以示範資料補正式缺漏。

## 目前仍不能自動驗收的事項

- 緊急聯絡、告知同意、適用照顧依據未有完整可信檢查來源，標為待負責人核對。
- 證照存在／未過期不等於通過受限制服務資格；目前正式資格政策仍待核准與串接。
- 基本資料存在不證明公司Google帳號本人已實際登入，不證明許可的法律適用性。
- DPA／跨境審查、安全交付、完整權限矩陣、備份還原與停機值班須提供外部驗收證據，未核准前不改為通過。
- `realDataIntakeApproved`及`fullLaunchApproved`固定為false；此唯讀清單不提供啟用正式營運開關，也不構成系統其他頁面的技術寫入封鎖。
