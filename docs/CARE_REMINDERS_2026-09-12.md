# 中央來源照顧提醒：本機實作與邊界

## 已實作

- 個案工作流程可掛載 `CareReminderCard({ context, clientId })`；只向照服員提供其指派範圍、具個案與健康欄位權限且已人工確認的提醒。
- 匯入解析預覽會整理候選提醒，但明示尚未關聯個案、尚未核對、不是正式照顧指示。
- 可信來源必須先通過既有上傳隔離解析、WORM 封存及授權，保存於 `private.import_upload_completions`。API 不接受瀏覽器傳入解析欄位或臨床事實。
- 有權限者可選擇可信批次，以穩定個案識別資料人工確認來源屬同一人，填寫理由後建立候選；此時資料庫從既有可信來源自動執行規則。
- 逐筆核對發布或不採用都須理由；已確認提醒可留理由撤回，但不修改原文、原始來源或照顧計畫。
- 新批次會替代舊批次的待核對佇列。已確認提醒仍保留，標示已有新來源需要重新確認，不自動覆寫。
- 所有來源、產生、審查、冪等操作資料皆私有、強制 RLS、禁止客戶端直接 DML；公開 RPC 為 security invoker 包裝，私有 definer 逐次驗證登入、機構、分支、個案與欄位權限。
- 來源關聯與審查保留既有最近 15 分鐘重新驗證要求，未新增員工登入授權。
- 查閱及異動有稽核，但不在 audit metadata 保存來源值、身分核對理由或臨床內文。

## 規則範圍

`cms-explicit-attention@1` 只支援四類：進食、移位、如廁、溝通協助。規則要求區段、精確欄位名稱、父層路徑及映射 key 一致，且來源值完全等於核准的明確文字選項。

不推斷數字選項、自由文字、否定句、診斷、藥名與藥量、飲食質地變更。缺值、不適用、未知、衝突、解析警示、被遮罩欄位、不同映射版本都不會被當作正常或生成指示。

目前通用解析器的 `mapped` 只代表已識別區段，不能當作完整官方 CMS 語意字典。主工作已在本機靜態檢查使用者提供的三份 HTML，僅輸出不含個案識別資料的欄位結構與通用選項文字；辨識 40、41、42 個區段，外部請求 0。將核實的 E1 吃飯、E7 上廁所、E8 移位、C4 表達完整標籤及需協助選項加入白名單，以匿名手寫 fixture 測試，未複製原始個案檔案到 repo。數字前綴不是判斷依據：必須完整選項文字相符；正常選項、單獨數字不會觸發。其他 CMS 題碼仍待字典驗收，第一版不宣稱覆蓋所有中央欄位。

## 尚未完成的外部門檻

- 本次未部署、未執行正式資料庫 migration 或建立雲端帳號。來源結構核對僅在本機唯讀執行；測試、程式碼及公開輸出未包含真實個案資料。
- 現有正式 HTML 匯入 storage/runtime 仍未完成接線；此功能不繞過該邊界。一般預覽批次不能假裝成可信封存批次。
- 提醒來源的回執固定 `formally_imported: false`。建立及發布機構提醒不等於中央身分、評估或核定計畫已正式匯入。
- 正式 Supabase、多 session 競態、真實照服員帳號及正式來源字典仍待驗收。

## 交叉審查後補強的日誌防線

本輪另針對日誌補了四項窄修，未改照服員的臨床判斷或自動勾選異常：

- 已觀察飲水但輸入空白時明確拒絕，不讓 `Number("")` 將缺值轉成 0；明確輸入 0 仍保留為實際觀察。
- 明確選擇如廁「需留意」時仍可保存不完整草稿，但提交與簽署必須有具體摘要、後續行動及本人確認異常旗標，程式不代填。
- 簽署佐證的角色清單僅包含當時有效、已生效指派且同機構的角色。
- 日誌 API 與頁面在讀取時均核對個案 ID；歷程必須屬於同次回覆的紀錄鏈，錯配時不呈現觀察內容。

聚焦測試：23 項 Vitest 通過；日誌 PostgreSQL 相容性測試 43/43 通過（使用真實執行長准入與合成 Google 身分，非准入繞過）。
