# 員工證照附件：後端候選與正式驗收邊界

## 結論

本輪補上證照附件的私有上傳、原件核對、安全掃描、獨立人工覆核、歷史清單與短效下載後端。**尚未接入員工前台、啟用正式掃毒、套用雲端遷移或發布正式環境。** 文件掃描通過、人工核驗通過、專業資格有效及可簽署量表是不同結果，不能互相代替。

舊頁72的證照版本仍不接受由呼叫者自行宣告的 `provided` 證明；本輪不修改其限制，也不變更胰島素、受資格限制服務或量表簽署條件。所有附件回覆固定 `serviceEligibility: not_evaluated`、`signable: false`。

## 已製作的流程

```text
選定既有證照版本 → 預留附件與原操作
  → 私有儲存（禁止覆寫）→ 回讀原件並核對 SHA-256
  → 已設定的 TLS 掃毒服務 → clean／infected／failed 不可變回條
  → 非上傳人、非證照本人之授權員工人工核驗
  → verified／rejected 不可變回條
```

- 上傳接受4MiB以內的PDF、JPEG、PNG；副檔名、宣告格式、檔案內容及PDF靜態結構均檢查，不靠檔名判定安全。
- 掃描使用儲存後實際回讀的原件，不使用瀏覽器宣稱的雜湊或掃毒結果。失敗、感染、逾時不視為安全；晚到的通過結果不會升級已保存的失敗結果。
- 相同人員、操作鍵與完整原輸入重試指向同一附件；換內容、版本、雜湊或操作用途不能沿用原鍵。完成附件若原件遺失，不會重新上傳後套用舊安全證據。
- 證明、掃描、人工核驗與操作帳本為不同不可變資料。瀏覽器不能直接修改表格或存取私有bucket；伺服器掃描完成介面也不授予資格。
- 一般已核准員工與管理員仍依機構、分支、實際生效角色及權限判定，不採公司網域或CEO例外作為全面放行。
- 本人只讀授權與管理權分離；已獲證照只讀權的員工可取得真正的MFA證據，但不能因此上傳或覆核他人附件。
- 附件操作使用實際Auth session、factor、AMR、challenge與近期事件證據。取得MFA資格不等於已完成驗證，也不新增管理權限。
- 前後兩次核對授權、來源版本及儲存物件身分；人員停用、角色撤回或原證照換版時拒絕現行版本操作。寫入與下載另核對近期驗證，逾期時拒絕；歷史清單使用有效AAL2及目前只讀權，不要求重新驗證即可查看授權metadata。SQL等待後失效的覆核會連同當次稽核與操作帳本回滾。
- 下載只針對目前有效來源、實際已掃描原件及未被拒絕的附件；讀回原件核對後產生60秒網址，重新查核授權才回傳。歷史清單最多50筆，明示總數與截斷，不將歷史資料當成目前可下載或有效資格。
- 清單/API使用private、no-store；錯誤不回傳堆疊、原件或敏感內部內容。下載檔名是通用名稱，不把證照本人姓名放入網址。

## API與啟用條件

| 入口 | 功能 | 必須具備 |
|---|---|---|
| `GET /api/staff-certificate-documents` | 指定證照及版本的授權歷史metadata，非原件下載 | 本人只讀或實際管理權、有效AAL2；權限與資料範圍再次核對 |
| `POST`，`x-staff-document-action: upload` | multipart預留、私有上傳、掃描 | 同源、讀取及管理權、近期真正AAL2、伺服器儲存密鑰及獨立用途掃毒核准 |
| `PATCH`，`x-staff-document-action: review` | 獨立人工核驗 | 同源、讀取及管理權、近期真正AAL2、已掃描安全、非上傳人且非證照本人 |
| `POST`，`x-staff-document-action: download` | 內容核對及短效下載 | 同源、本人只讀或管理權、近期真正AAL2、現行來源及原件再次核對 |

寫入與下載接受原 `idempotency_key`。下載本身不產生業務版本；每次仍重新授權、記錄查核並產生短效連結，不承諾相同網址。API接受的來源版本及內容雜湊必須與正式已保存證照一致，不能由附件建立任意證照版本。

獨立的 `STAFF_CERTIFICATE_DOCUMENTS_SCANNER_APPROVED` 不會因個案文件已核准而自動開啟；還須滿足既有TLS掃描器設定與核准條件。缺任一條件，上傳回503且不預留或傳送檔案。測試使用合成原件與假掃描依賴，不曾把真實員工文件送到第三方。

## 仍需處理的恢復限制

- 每階段有硬逾時，逾時不代表遠端未保存；已發出的儲存或SQL操作可能晚完成。不可用新鍵直接重送，須先對帳原操作及原件。
- 未完成 `reserved` 附件保留原上傳者的session、challenge與預留時間。原證據／預留期限已過時，重新MFA也不會以舊鍵延長原掃描資格。此時需授權的只讀對帳、明確過期結果及核准的新操作恢復流程；**本輪尚未製作此管理流程**，不能宣稱所有逾時均能直接重試恢復。
- `uploadedAt` 是伺服器預留時間，非儲存供應商實際收件或掃描完成時間；介面須分別呈現，不能拿來證明實際上傳時點。
- 尚無前台原操作journal、整頁重新載入定位、附件人工處置或自動背景續傳。此API不是員工已可使用的上傳入口。
- 短效網址一旦已交付，最長60秒內仍可能有效；重新核權不代表已交付網址可即時撤銷。高敏感用途若要求即時撤銷，須另設逐次驗證的下載代理。

## 下一階段與正式門檻

1. 先補非CEO管理員／本人只讀可使用的授權證照來源清單與SSR投影，再將上述後端接入頁72：選員工／證照版本→上傳→查看掃描狀態→由獨立人員核驗。舊頁72仍依原證照snapshot的登入限制，新的附件API可通過不代表該頁已可載入；不可全域放寬舊證照writer。先做好過期、未知結果及原操作回查，不能只新增成功按鈕。
2. 製作以可信附件及核驗回條建立 `provided` 證照新版本的交易；凍結舊版，確認資格、登錄、生效／到期與受限制服務的實際規則，不能接受呼叫者自行標記verified。
3. 接入逐表核簽資格政策及正式量表採用／風險確認／簽署／更正版。附件核驗不能自動簽署或讓未具資格人員執行受限制服務。
4. 完成掃毒供應商、員工資料用途、區域、保留／退出、私有儲存與備份審查及實際原件測試。普通Supabase Storage不宣稱WORM，也不替代原CMS不可變封存要求。
5. 再依[完整正式部署門檻](FORMAL_DEPLOYMENT_CHECKLIST_2026-09-26.md)排演精確增量遷移、真人員工登入、上傳／核驗／撤權、資料還原與回滾。商用方案及資料區域尚未核准，不擅自增加費用或移動真實資料。

本輪補的是正式資格鏈的附件後端缺口，並非「所有89頁已可正式使用」或「明天可直接上線」的證明。
