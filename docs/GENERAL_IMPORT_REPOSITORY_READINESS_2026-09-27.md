# 通用 CMS 正式儲存候選：部署與驗收界線

本輪只補 **25 MiB 通用匯入的持久化暫存**，尚未發布。不是全部89頁驗收、真實雲端封存或正式資料移轉證明。4 MiB 單案收案仍使用既有核准 Google AAL1 流程及基本資料交易，不因這輪新增通用儲存而改變。

## 已實作的閉環

- 四個通用入口依目前登入者及動作建立每請求獨立 repository；正式模式不退回記憶體或展示資料。未設定東京封存、KMS與後端工作憑證仍明確停止。
- 上傳先使用既有受控預約、可信伺服器靜態解析、不可變封存及完成回執，再建立通用暫存版本。來源由已完成且具真正驗證證據的預約推導，不能由瀏覽器送來的解析結果或物件位置取代。
- 原件讀回核對確切封存版本、位元組數、SHA-256及機構／分支；重新解析前後重驗來源版本及目前權限。未知欄位、衝突、警示與解析安全報告完整保存。
- 第150份增量只新增私有來源、不可變版本及原操作回執。三張表執行FORCE RLS且不提供一般帳號／service_role直接DML；公開介面使用窄範圍受控交易，查閱亦留下不含欄位值的稽核。
- 原操作鍵共用同一身分帳本，跨動作或不同內容重用拒絕；回查／重送取得確切歷史版本，不假冒最新列表。相同檔案另建去重回執，保存原批次作者而非改寫為本次操作人。
- 重新解析只支援既有`central-care-plan-html@1`，必須與可信來源的既有解析結果一致。未來映射版本需要另外發布，不接受客戶端自訂新版。
- 新增、重新解析、核准均重新核對真正驗證器證據及近期15分鐘時效；資料庫直接寫入同樣拒絕未來時間。預覽維持實際AAL2授權，但不新增15分鐘要求。
- 對RPC、封存及回讀設置同一repository建構起算20秒期限，超時停止後續步驟並保留原操作。初始登入查詢、建立cookie client及完整HTTP傳輸不在此期限內，不宣稱整個請求已達20秒上限。

**核准結果只凍結暫存：** `staging_only: true`、`formally_imported: false`。本輪不寫入個案、核定照顧計畫、額度、醫囑、量表分數、資格、申報或簽署資料，不能將回執文字改成正式入檔。

## 已發現並修正的問題

1. 實際資料庫首次建立來源時少傳雜湊欄位，造成SQL42601；補齊參數，未放寬來源檢查。
2. 核准交易的JSON欄位別名與預約變數撞名，造成SQL42703；使用明確欄位別名。
3. 既有MFA共用helper容許少量未來時差；本輪通用寫入增加實際證據的非未來檢查，不修改其他模組的共用規則。
4. 不得用「最近驗證成功」布林值製造現在時間；保存資料庫回傳的真正驗證時間，並在遠端等待後重驗授權。
5. 原本預約回覆後仍可能在撤權狀態封存原件；補上預約、封存、完成交易的前後授權檢查。已在途的不可變物件無法假裝撤回，保留對帳及結果未知邊界。
6. 五個原生驗收runner仍鎖定149份migration；更新為精確150份及新末版檔案，未放寬斷言、權限或逾時。
