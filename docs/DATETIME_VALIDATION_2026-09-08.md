# 日期時間驗證收斂（2026-09-08）

## 修補的問題

舊式「包含 Z／offset，再檢查 `Date.parse` 有限值」的驗證會接受不存在的曆日。例如 JavaScript 可把 `2026-02-30T10:00:00+08:00` 正規化成三月，造成輸入日期與保存日期不同。

這次只修正接受／拒絕規則，沒有改寫任何既有資料、簽署版本、公式、服務金額或權限。若歷史輸入曾被正規化，無法由現存時間反推原意，須由資料負責人另行確認並建立更正版。

## 已實作

- `src/lib/integrations/datetime.ts` 提供共用 `isStrictOffsetDateTime`，先以本專案已安裝 Zod 的日期時間驗證核對有效曆日、閏年、時間與 offset，再轉換成 UTC。
- 保留分鐘精度、秒／小數秒、正負 offset，以及小寫 `t`／`z` 的相容性；拒絕未帶時區、日期文字敘述、24:00、非法 offset、空白尾綴及過長輸入。
- `parseIsoDateTime` 仍保留原本有界 min／max 與結構化錯誤碼。
- 既有 113 個 library 檔案中的 114 處相同弱判斷已機械性替換為共用驗證。周邊狀態機、權限、雜湊及交易邏輯未改動。
- 同時施工的家屬、個案服務紀錄與稽核專用模組由其各自負責人收斂，避免覆蓋進行中的工作。
- 新增來源檢查，防止已知的弱判斷再次出現在 production library；此檢查不是對所有可能日期解析方式的安全證明。

## 本機證據與限制

- 共用 validator：28 項測試通過，包含閏年／世紀例外、UTC 跨日、offset、有效精度、非法曆日、無時區、邊界與來源回歸檢查。
- 機械替換後第一輪完整 Vitest：253 檔／2,400 項通過；其後新增的測試與模組仍須納入最終整合重跑，不能沿用這次數字宣稱新增程式已驗證。
- 這是程式與本機相容性修補，不是正式 Supabase、瀏覽器所有日期選擇器、歷史資料清理或正式部署驗收。
