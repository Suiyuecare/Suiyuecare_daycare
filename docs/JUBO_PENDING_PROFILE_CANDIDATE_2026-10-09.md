# JUBO 待收案完整資料版本：候選驗收（不得部署）

此候選交易須先通過原始 XLSX 同位元組解析、23/17 核對、23/23 逐筆主管 AAL2 核准，才可由資料庫擁有者執行。它不授權出勤、服務、用藥、交通或申報，也不從 JUBO 開案日／首次服務日推定本機構收案日。**目前尚無 v2 正式覆核介面或 RPC，故真實個案 promotion 必然拒絕；舊 v1 的 23 筆核准不能沿用。**

## 同一交易的產物

- 23 筆 `public.clients` 均為 `pending`、`admitted_on=NULL`、`ended_on=NULL`；17 筆月清冊只供核對，不另建個案。
- 每筆必有 `private.client_intake_versions` 第 1 版，包含姓名、生日、正規化身分識別、性別、戶籍／居住地址、CMS 等級、身障資訊、主要聯絡人／代理人與待確認同意。空白值保持空白；個案電話不由其他電話欄位猜測。
- 每版以 `private.jubo_intake_profile_sources` 連回不可變原始主檔列、可選月清冊列、原始列 SHA-256、欄位索引、解析／映射版本與待補警示。原值由連結的 `private.jubo_source_rows.raw_values` 及 `column_labels` 讀取；v2 顯示值留在 profile，另保存 `normalization_field_indices` 與 `mapping_review_sha256`，稽核與回條不回傳姓名、證號或地址。
- 任一列不符來源型別、身分雜湊、欄位驗證或 FK 時，整批交易回滾；相同冪等鍵重送只回同一回條，不能再建立版本。

## 主權與目前硬阻擋

JUBO 是經核對的廠商匯出，不是中央 CMS 的官方權威。第 1 版欄位標示 `jubo_export`，不冒充 `central`；正式 CMS 匯入仍須逐欄人工確認，不能以後來資料靜默覆寫來源。現有 `private.write_intake_profile` 及個案主檔編輯投影不開放 `pending`；新增的資料庫護欄對此批個案即使日後解除待收案，也拒絕無正式 CMS 來源的第 2 版。故目前主管**可以看來源及缺漏，但尚不能在此候選版補資料**。另需獨立設計「機構補充欄位」的狹義 allowlist、版本與覆核，不能只把 `pending` 加進通用更新狀態清單。

本 SQL 以已審查的來源列重建 JUBO 規劃器對應欄位；內部個案代碼採資料庫新建代碼，不假稱等於規劃器以機密 HMAC 產生的候選代碼。兩份實際核准 XLSX 在隔離本機完成 planner 與候選 SQL 的映射對照，但尚未證明正式入庫 worker 的 staged rows 與核准 XLSX 位元組完全一致；亦未完成所有模組對 `pending` 狀態的解析／讀寫隔離、真實 PostgreSQL 併發、真人 AAL2、東京搬遷及完整前端驗收。因此即使 PGlite 合成測試通過，**不可將此候選 promotion 合併、發布、部署或用於真實個資**。

## v2 映射與本機聚合驗證

聯絡人原始儲存格中的控制字元，僅在顯示欄改為可見的 ` / ` 分隔；不合併人名、推定關係或改寫原始列。原來的 NFKC 顯示正規化仍適用，但其相容字形可能影響人名／其他文字語義，因此每一筆有異動的個案均標 `REVIEW_SOURCE_NORMALIZATION`，以原始儲存格、顯示欄及變動欄位索引由主管逐筆核對。v2 指紋以來源列 SHA、固定映射版本、去除尚未產生的 clientCode 之顯示 profile、正規化欄位索引組成；`private.jubo_profile_mapping_v2_reviews` 是獨立於舊來源列審核的不可變新表。候選交易只接受此表中最新、指紋相符的 `approved`，舊 v1 列審核無法滿足它。此表雖要求重新驗證紀錄 FK，**尚無正式 RPC 驗證該證據的新近度、目的與真人操作；不得將本機合成測試插入視為已完成 AAL2 驗收。**

2026-10-09 在隔離本機執行核准雙檔比對，沒有寫入正式資料庫或輸出個資：主檔 23、月清冊 17、連結 17；40 個身分鍵、327 個原始映射欄路徑、138 個 staging 核心欄位、85 個月表交叉欄位、598 個 profile 葉欄位及 152 個正規化索引葉欄位均相符，差異 0。23/23 筆建立 v2 候選覆核指紋；60 個映射欄位涉及 NFKC 變化、46 個聯絡欄位含需顯示分隔的控制字元，23/23 筆都須重新人工確認。核准來源中映射欄位的精確 `null`／空字串及文字 `不適用` 各為 0；合成測試另覆蓋 null 與不適用的區別。按主檔列序拼接 23 個 v2 指紋後的單一聚合 SHA-256 為 `63b81fe5d9c82a13f656f1fa82820b007829e85e0cb6f28c349ece462c8c9e3a`；**不得將此聚合值當作 23 筆真人覆核。**

仍缺正式上傳 worker 對 staged rows 的交易寫入與讀回對帳，以及可供主管查看原值／顯示值、逐筆決定並完成新 AAL2 驗證的 v2 覆核流程；實際備援 PostgreSQL 與併發驗證也未做。這些是硬阻擋，不因本機逐欄比對通過而解除。
