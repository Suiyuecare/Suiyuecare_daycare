# JUBO 雙檔暫存放行閘（2026-10-10）

本文件區分「來源檔可讀」、「私有暫存」、「待收案個案」及「正式服務」。任何前一階段的成功回條，都不等於後一階段已完成。此候選分支不得直接發到正式資料庫，亦不得把月清冊當作出勤。

## 已取得的來源證據

- 核准的主檔 XLSX 為 23 筆個案及 1 筆末端非個案註記；月清冊 XLSX 為 17 筆，全部以精確身分鍵對回主檔，不能再建 17 筆個案。
- 主檔來源狀態為 17 筆服務中、1 筆暫停、5 筆結案。JUBO 開案日及首次服務日均不得推定為本機構正式收案日或出勤。
- 來源兩檔的 SHA-256 鎖定於 `src/lib/jubo-import/xlsx-reader.ts`，實際檔案及個資不得加入 Git、測試輸出、HTTP 錯誤或一般紀錄檔。
- 目前來源清單不含足以核對七年服務、附件與簽章的正式全量明細，因此主檔與歷史服務的驗收必須分開。

## 候選上傳入口的邊界

`POST /api/jubo-source-stage` 只接收 `master`、`monthlySummary` 兩份 XLSX 與 `footerReviewReason`。呼叫須來自正式站同源頁面，帶固定 UUID 冪等鍵；入口與私有資料庫各自檢查員工、機構、分支、`imports.manage`／`imports.approve` 及近期雙因子驗證。實際串流最多 2 MB，每檔最多 1.5 MB，解析前檢查原始檔雜湊與 23／17 配對。

成功只回傳操作編號、列數、來源狀態總數和「僅暫存／未正式匯入」標記；不回傳檔案、個案欄位、原始雜湊或儲存位置。此入口目前預設關閉，不能作為「23 筆已移轉」證據。重試須沿用原冪等鍵；結果不明時不能以新鍵再送。

## 東京切換前的硬條件

東京專案現有 JUBO 基礎來源表，但沒有來源批次或個案；機構、分支及 Auth 使用者亦未建立。候選分支的後續 SQL **不能整包直接套到東京正式庫**：先切分正式放行集，在隔離的受控 PostgreSQL 完成 ACL／RLS、失敗回滾、並行冪等、每人限流及 50 人並行壓測、備份還原，再由授權人員審核變更。正式站仍連首爾時，不得聲稱已遷往東京。

來源 XLSX 暫存於私有資料庫欄位，不是 S3 Object Lock，也不是七年不可刪改封存的證明。上線前需確認保存、備份、退出、審計與資料處理協議；CMS 正式 HTML 上傳仍依既定決定維持停用。

## 安全回退

未完成 B 至 E 的前置條件時，保持 JUBO 暫存與覆核旗標關閉，不變更正式 Supabase 專案 URL，不從候選表補出「已收案」狀態。任何提交結果不明時，先使用原冪等鍵查回執並核對資料庫；不得改用新鍵重送同一雙檔。正式資料零寫入才可視為未移轉，不能以畫面顯示空白推斷交易失敗。
