## 東京新專案與資料庫切換門檻

1. 使用者確認 Supabase 組織，查詢並再次確認新增專案的實際費用後，才建立 `ap-northeast-1` 專案。已查得現有 `Suiyuecare's Org` 新增專案為 US$10／月，仍待使用者確認這個**確切**組織與金額。首爾專案保持原狀，不刪除。
2. 用 PostgreSQL 17 的 `pg_dump`／`psql` 或官方等效方法，先在加密、限制權限的本機目錄製作邏輯備份（角色、schema、資料、`auth` 與 `supabase_migrations`）。首爾的實體備份不能跨區直接還原。備份後核對雜湊、物件數與關鍵資料筆數。參考 [Supabase 區域變更](https://supabase.com/docs/guides/troubleshooting/change-project-region-eWJo5Z) 與 [CLI 邏輯備份／還原](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)。
3. 在東京還原並驗證所有資料表、RLS、函式、Auth 使用者與 Google 身分、待開通邀請、Storage bucket、版本及稽核紀錄；備份目錄與輸出不得寫入 Git 或一般紀錄檔。重新設定 Google Provider、回呼網址、Auth URL、伺服器端密鑰和 Vercel 環境變數。不能只更換公開 Supabase URL。
4. 在切換窗口先凍結正式寫入，再做最後增量／差異核對。東京預覽環境必須通過 CEO／主任實際登入、跨分支隔離、收案讀寫、量表草稿、附件讀取與還原演練；失敗就保持首爾正式運作。
5. 只有東京驗收全過才切換 `daycare.suiyuecare.com` 的 Vercel 正式環境，核對部署 Ready、網域、執行時錯誤和資料筆數。東京開始接受寫入後，回退首爾需要反向對帳，不能只切回舊網址。

## Jubo 匯入門檻

1. 原始兩份 XLSX 先掃描、驗證 MIME／大小／SHA-256，封存在東京私人儲存；保留未被映射的欄位與重複欄名的位置，不把個資存入程式碼或公開儲存。
2. 套用 `jubo-master-monthly-202610-v1` 欄位對照，23 筆主檔與 17 筆月表的筆數、身分識別碼、日期、狀態、欄寬全部檢核。衝突與未知值一律停止；匯入人先看差異及用途，再由具權限且完成近期 AAL2 驗證的操作人核准。
3. 核准後以冪等鍵建立正式個案基本資料並將原始來源列連結到個案；不得自動建立已簽署量表、用藥、同意或出勤紀錄。既有個案如有身分或編號碰撞，必須人工審核，不能覆寫。
4. 驗收：正式個案與來源 23/23 精確對帳；月表 17/17 正確連結；每筆原始欄位 95/95 或 191/191 可取回；重送 0 重複、跨分支外洩 0、正式醫療／簽署資料偽造 0。未取得七年歷史與附件前只標示「基本資料已移轉」，不可標示「全部歷史完成」。
