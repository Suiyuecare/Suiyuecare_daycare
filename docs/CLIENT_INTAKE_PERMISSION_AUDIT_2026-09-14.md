# 收案流程上線前權限複核

檢查日期：2026-09-14。範圍為 CMS／基本資料、每週到站接送、臺北 A／B／C 草稿、六類私有附件；另回歸既有 Google 核准與 11 職務模板。全部測試使用本機合成資料。本報告不表示已部署、已開通正式帳號，或正式 Supabase／Google／Storage 登入鏈已完成驗收。

## 發現與修正

### P1－A 表可繞過敏感基本資料撤權（已修）

原 A 表沿用舊 ABCD 評估權限，撤除 `clients.demographics.read` 後仍可取得生日、地址、聯絡人及既存草稿回條。新增兩個負向測試在修改前均出現「沒有例外」，證實不是僅推測的問題。

- 資料庫在 `supabase/migrations/20260913175206_taipei_abcd_intake_drafts.sql:98` 的同一讀寫 guard 加入 A 表個案層級敏感欄位檢查；重送仍先重新驗證權限。
- API 在 `src/app/api/taipei-abcd/drafts/route.ts:18` 對 A 表做相同防守，未把護理／社工／照服等職稱當作繞過條件。
- 回歸：`supabase/tests/taipei_abcd_intake_drafts.test.sql:136`。撤權後 A 讀取及歷史操作重送被拒；獨立 B 草稿權限沒有被一起誤封。

### P1－身分證影像可繞過敏感基本資料撤權（已修）

原附件分類只檢查 `clients.manage`。撤除 demographic 權限後，身分證清單、歷史版本、下載、原上傳重送、原覆核重送仍成功，五個新負向測試先全部失敗。

- `supabase/migrations/20260913180653_client_documents_intake_pipeline.sql:56` 統一要求身分證正反面具備個案管理及敏感基本資料權限；保留跨機構／分支／個案及近期身分驗證條件。
- `src/app/api/client-documents/route.ts:36` 拒絕與角色範圍不符的回傳清單；下載簽網址前、上傳前、覆核前也驗證分類權限。
- 回歸：`supabase/tests/client_documents_intake_pipeline.test.sql:98`。撤權後五條路徑全被拒，駕駛的六類附件仍全部受限。
- 只修未發布 migration 與 API，沒有給任何人或模板補權限。

### P2－Google 一般登入不等同高風險重新驗證（仍需作業政策確認）

此批保留既有 AAL 邊界。`src/lib/client-intake/server.ts:17` 的主檔修改、`src/app/api/client-weekly/route.ts:30` 的週表修改及附件操作仍需近期 AAL2；A／B／C 草稿沿用舊 ABCD 的 AAL2。A／B／C 的 SQL 與 GET API 都沒有 CEO AAL1 唯讀例外，所以不是只修 API 就能解決的讀取不一致。

若要將特定非簽署作業調整為 Google 加核准角色，必須另有明確政策、窄範圍實作及負向測試，不能把已登入直接當成 AAL2。正式簽署、給藥、匯出或權限調整不應因此一起放寬。

## 實測證據

- 基線六套 SQL：392 項通過，含四個新流程、executive Google、11 職務，全部使用真實 admission predicates（合成身分）。
- 修正後 A／B／C 與附件兩套：106 項通過（56＋50），新增七個原先失敗的撤權檢查均轉綠。
- 新角色矩陣、CEO 唯讀、原 ABCD：173 項通過（9＋110＋54）。原 ABCD 是既存 PGlite-only admission fixture 套，保留原角色／AAL／簽署約束；不得稱為正式 Google 全鏈驗收。
- API 與角色 Vitest：五檔共 54 項通過；含新增 A 欄位撤權、身分證清單／上傳／覆核／下載防守。
- 角色 taxonomy 升級：20 項通過，確認不改舊帳號、角色指派、臨床紀錄及既有稽核。
- 修改 API／schema／測試的 ESLint 通過；沒有測試為了過關而補正式 grant。
- 上述數字包含重疊回歸，不能加總成全系統唯一測試數。原生 PostgreSQL 與完整發布回歸由另份 preflight／發布紀錄記載。
